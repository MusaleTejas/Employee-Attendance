# REVIEW.md

Review of the starter `app/main.py` — helpers and provided endpoints.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How I fixed it |
|---|---|---|---|---|
| 1 | `list_employees` (line 93) — `skip = page * page_size` | Off-by-one in pagination. Page 1 should skip 0 records; the code skips `page_size` records instead, so the first page is empty and the second page shows what the first should. | Request `GET /employees?page=1&page_size=20`; the response is empty even though employees exist. | Changed to `skip = (page - 1) * page_size`. |
| 2 | `list_employees` (line 95) — `count_documents({})` | The total count ignores the `department` filter. A filtered list returns the correct rows but reports the wrong `total`. | Request `GET /employees?department=Engineering`; items are filtered but `total` is the count of all employees. | Changed to `count_documents(q)` where `q` already has the department filter applied. |
| 3 | `list_employees` — no sort | The contract requires results sorted by `emp_code` ascending. The starter has no `.sort()` call, so order is MongoDB's default insertion order. | Request employees; the order is not alphabetical by `emp_code` and is not stable across insertions. | Added `.sort("emp_code", ASCENDING)`. |
| 4 | `punch_in` (line 102) — `datetime.fromtimestamp(body.punched_at / 1000)` | Uses naive (no time zone) datetime and does not truncate sub-second precision. The contract says instants are truncated to whole seconds (R1) and stored as BSON datetimes (UTC). A naive datetime is ambiguous: PyMongo writes it as if it is UTC, but `datetime.fromtimestamp` in a non-UTC system returns a local-time value. | Run the server on a machine with IST as the local time zone; the stored UTC datetime will be off by 5.5 hours. Also, a `punched_at` with milliseconds below 100 billion (i.e., seconds-range) is not rejected. | Converted `punched_at` to UTC explicitly using `datetime.fromtimestamp(sec, tz=timezone.utc)` with the value divided by 1000 and truncated to whole seconds. Added a validator that rejects values outside the valid epoch ms range. |
| 5 | `punch_in` (line 104) — check-then-insert race | The duplicate check uses a separate `find_one` before `insert_one`. Two concurrent requests for the same employee and date can both pass the check and both insert, violating the one-record-per-day constraint. | Send two simultaneous punch-in requests for the same employee and date; both may return 201. | Removed the pre-check. Rely solely on the unique index on `(emp_code, date)` and catch `DuplicateKeyError` from `insert_one`. |
| 6 | `punch_in` (line 102) — no 404 when employee is not found | If `body.emp_code` does not exist, `emp` is `None`. The next line (`emp["shift_start"]`) raises an unhandled `TypeError`, which FastAPI returns as a 500. The contract requires a 404. | POST `/attendance/punch-in` with a non-existent `emp_code`; the server returns 500 instead of 404. | Added an explicit `if not emp: raise HTTPException(404, ...)` check immediately after the `find_one`. |
| 7 | `list_attendance` (lines 144–150) — loads the full collection into memory | The code fetches every matching document with `find(q)`, sorts them in Python, then slices. On a 100,000-record collection this is very slow and uses large amounts of memory. The contract explicitly says the endpoint must stay fast. | Query the endpoint on a large dataset; the server is slow and may run out of memory. | Moved sorting to MongoDB using `.sort(...)` and applied `.skip()` and `.limit()` before returning. `count_documents(q)` is used for the total. |
| 8 | `list_attendance` (line 144) — total uses wrong count | The code sets `total = len(docs)` after fetching only the current page's rows (after slicing). With the in-memory approach it fetches everything first, so `total` is accidentally correct, but it is conceptually wrong: `total` should be the count of all matching records, not the count on the page. | With the corrected cursor approach this becomes a real bug: `total` would only count the page. | Changed to `total = db.attendance_logs.count_documents(q)` before applying skip/limit. |
| 9 | `compute_late_minutes` (line 36) — grace period uses `> 10` minutes, not `> 10:00` | The check `if minutes > 10` compares whole-minutes elapsed, so 09:40:00 (exactly 10 minutes) returns 0 correctly, but 09:40:01 should return 10 (R2 example), not 0. The floor of `(punch_in - shift_start)` in minutes for 09:40:01 is 10, and 10 is not > 10, so the function incorrectly returns 0. The test is `minutes > 10`, but R2 says "strictly more than 10:00", meaning `total_seconds > 600`. | Punch in at 09:40:01; `late_minutes` is 0 (wrong), should be 10. | Changed the comparison to `total_seconds > 600` (using raw seconds, not minutes), then take `int(diff_seconds // 60)` for the result. |
| 10 | No indexes created | The starter has no `create_index` calls. The contract requires indexes to be created idempotently at startup, and the grader checks that explain plans show `IXSCAN` on a ~100k-record dataset. Without indexes every query is a collection scan. | Run `explain` on any endpoint; the plan shows `COLLSCAN`. | Added `create_indexes()` called at module load, creating unique indexes on `employees.emp_code` and `attendance_logs.(emp_code, date)`, plus supporting indexes for the list and analytics queries. |

## Items reviewed and not considered defects

- **`compute_overtime`**: The helper in the starter used `datetime.fromisoformat(date_str)` as the base for shift_end, which is one valid approach. I rewrote the function to work directly from the IST representation of `punch_out`, which handles overnight shifts more cleanly, but the original logic was not clearly wrong for normal shifts.
- **`create_employee` `created_at`**: `datetime.now()` returns a naive datetime, which PyMongo stores as UTC by convention. This is a latent bug on non-UTC servers, but the API does not specify the server's time zone, so it is not verifiably incorrect. I changed it to `datetime.now(tz=timezone.utc)` for clarity.
- **`health` endpoint**: Returns `{"status": "ok"}` without actually pinging MongoDB. The contract says it should return 503 if MongoDB is unavailable. I added a `db.command("ping")` call.
